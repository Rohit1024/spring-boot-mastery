0009: Global Exception Handling with @RestControllerAdvice & ProblemDetails¶

In production systems, unhandled exceptions lead to ugly Whitelabel Error Pages, leak internal Java stack traces and SQL queries to potential attackers (OWASP Security Risk), and degrade API client ergonomics.

In this lesson, we master centralized global exception handling using @RestControllerAdvice, extend ResponseEntityExceptionHandler, and implement the modern RFC 7807 / RFC 9457 ProblemDetail standard introduced in Spring Boot 3.x.

1. Exception Handling Architecture in Spring MVC¶

When an uncaught exception is thrown inside a Controller, Service, or Repository, the DispatcherServlet catches it and delegates resolution to the HandlerExceptionResolver chain:

sequenceDiagram
    autonumber
    actor Client as 🌐 Client
    participant DS as ⚡ DispatcherServlet
    participant Ctrl as 🎮 @RestController
    participant Service as 💼 OrderService
    participant HER as 🛡️ HandlerExceptionResolverComposite
    participant Advice as ⚠️ GlobalExceptionHandler (@RestControllerAdvice)

    Client->>DS: GET /api/v1/orders/999
    DS->>Ctrl: getOrderById(999)
    Ctrl->>Service: findById(999)
    Service-->>Ctrl: throw new ResourceNotFoundException("Order 999 not found")
    Ctrl-->>DS: Uncaught ResourceNotFoundException propagates

    DS->>HER: resolveException(request, response, handler, ex)
    HER->>Advice: Match @ExceptionHandler(ResourceNotFoundException.class)
    Advice-->>HER: ResponseEntity<ProblemDetail> (HTTP 404)
    HER-->>DS: Resolved Response
    DS-->>Client: HTTP 404 Not Found (RFC 9457 JSON Body)

2. The RFC 7807 / RFC 9457 ProblemDetail Standard¶

Starting in Spring Boot 3.x / Spring Framework 6, Spring natively implements RFC 9457 ("Problem Details for HTTP APIs") via org.springframework.http.ProblemDetail.

Why Standardized Error Schemas Matter:¶

Instead of every company inventing its own ad-hoc error format ({"err": "failed"} vs {"error_message": "failed"}), RFC 9457 establishes a universal JSON schema:

{
  "type": "https://api.example.com/errors/resource-not-found",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "Order with ID '999' was not found in the system.",
  "instance": "/api/v1/orders/999",
  "timestamp": "2026-08-17T12:00:00Z",
  "traceId": "c8a4f91b"
}
Field Meaning
type A URI reference that identifies the problem type and provides human-readable documentation.
title A short, human-readable summary of the problem type (should not change between occurrences).
status The HTTP status code generated by the origin server for this occurrence.
detail A human-readable explanation specific to this particular error occurrence.
instance A URI reference that identifies the specific endpoint invocation where the problem occurred.

3. Production-Ready @RestControllerAdvice Implementation¶

Let's build a unified global exception handler handling validation failures, domain exceptions, malformed JSON, and catch-all server errors:

Step 1: Define Custom Business Exceptions¶

package com.example.demo.exception;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ResponseStatus;

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String message) {
        super(message);
    }
}

public class BusinessRuleViolationException extends RuntimeException {
    public BusinessRuleViolationException(String message) {
        super(message);
    }
}

Step 2: Implement the Global Exception Handler¶

package com.example.demo.exception;

import jakarta.servlet.http.HttpServletRequest;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.ServletWebRequest;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

import java.net.URI;
import java.time.Instant;
import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // 1. Handle Bean Validation Failures (@Valid / @NotBlank / @Min)
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex,
            HttpHeaders headers,
            HttpStatusCode status,
            WebRequest request) {

        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "One or more input fields failed validation constraints.");

        problemDetail.setTitle("Invalid Request Payload");
        problemDetail.setType(URI.create("https://api.example.com/errors/validation-error"));
        problemDetail.setProperty("timestamp", Instant.now());

        // Extract field-level errors
        Map<String, String> invalidFields = new HashMap<>();
        for (FieldError fieldError : ex.getBindingResult().getFieldErrors()) {
            invalidFields.put(fieldError.getField(), fieldError.getDefaultMessage());
        }
        problemDetail.setProperty("invalidFields", invalidFields);

        return new ResponseEntity<>(problemDetail, HttpStatus.BAD_REQUEST);
    }

    // 2. Handle 404 Resource Not Found Exceptions
    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleResourceNotFound(ResourceNotFoundException ex, HttpServletRequest request) {
        log.warn("Resource not found: {}", ex.getMessage());

        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problemDetail.setTitle("Resource Not Found");
        problemDetail.setType(URI.create("https://api.example.com/errors/not-found"));
        problemDetail.setInstance(URI.create(request.getRequestURI()));
        problemDetail.setProperty("timestamp", Instant.now());
        return problemDetail;
    }

    // 3. Handle Domain / Business Rule Violations (409 Conflict)
    @ExceptionHandler(BusinessRuleViolationException.class)
    public ProblemDetail handleBusinessViolation(BusinessRuleViolationException ex, HttpServletRequest request) {
        log.warn("Business rule violation: {}", ex.getMessage());

        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, ex.getMessage());
        problemDetail.setTitle("Business Rule Violation");
        problemDetail.setType(URI.create("https://api.example.com/errors/business-conflict"));
        problemDetail.setInstance(URI.create(request.getRequestURI()));
        problemDetail.setProperty("timestamp", Instant.now());
        return problemDetail;
    }

    // 4. Catch-All for Unexpected Server Errors (500 Internal Server Error)
    @ExceptionHandler(Exception.class)
    public ProblemDetail handleUnexpectedException(Exception ex, HttpServletRequest request) {
        String traceId = MDC.get("traceId");
        log.error("Unhandled server exception [traceId: {}]: ", traceId, ex);

        // Security rule: NEVER expose raw exception message or stack trace to client!
        ProblemDetail problemDetail = ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR,
                "An unexpected internal error occurred. Please contact support with trace ID: " + traceId);

        problemDetail.setTitle("Internal Server Error");
        problemDetail.setType(URI.create("https://api.example.com/errors/internal-error"));
        problemDetail.setInstance(URI.create(request.getRequestURI()));
        problemDetail.setProperty("traceId", traceId);
        problemDetail.setProperty("timestamp", Instant.now());
        return problemDetail;
    }
}

4. Enabling RFC 7807 Globally in application.yml¶

Spring Boot 3 allows you to enable RFC 7807 ProblemDetail responses automatically for standard framework exceptions by adding:

spring:
  mvc:
    problemdetails:
      enabled: true

When enabled, Spring MVC converts missing request parameters, unsupported media types (415), and unhandled routing errors (404) directly into RFC 7807 JSON responses without manual handler code.

6. Knowledge Check & Retrieval Practice¶

Question 1: Why should internal exception messages and stack traces never be returned to the API client in production?

Answer: Exposing stack traces leaks internal database structures, framework versions, and class paths to attackers, violating the principle of least privilege.

Question 2: What is the benefit of extending ResponseEntityExceptionHandler in your @RestControllerAdvice class?

Answer: It provides centralized override hooks for all standard Spring MVC exceptions (HttpRequestMethodNotSupportedException, MethodArgumentNotValidException, etc.).

Question 3: In RFC 9457 Problem Details, what is the purpose of the instance field?

Answer: It specifies the exact URI endpoint where the error occurred, providing context for distributed tracing and client debugging.
